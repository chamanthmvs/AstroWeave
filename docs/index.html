Astrology, orchestrated.

AstroWeave is a hierarchical reasoning system where a central Astrologer Manager coordinates specialists, methodologies, tools, and knowledge to turn one natural-language question into one considered answer.

01 / the system

One question. Multiple perspectives.

A user should not need to know which specialist, astrology system, tool, or knowledge source is required. AstroWeave determines how the question should be analyzed, delegates the work, evaluates the results, and coordinates the final synthesis.

Domain is not methodology.

AstroWeave keeps the subject of a question separate from the system used to interpret it. That boundary is the foundation for adding new specialists and new methodologies without rebuilding the architecture.

03 / the manager

Coordination above complexity.

The Astrologer Manager is the top-level intelligence. It coordinates the system without absorbing the detailed reasoning logic of every specialist.

05 / current implementation

v1 works end to end. The system is still in progress.

AstroWeave can accept a question and birth details, create a chart-backed specialist analysis, and synthesize an answer. It is an active prototype, not a production service.

AVAILABLE NOW

End-to-end flow

Streamlit submits a question to FastAPI. The orchestrator selects career, finance, love, or sports specialists, retrieves one birth chart, and combines their conclusions.

CONFIGURABLE

Models and charts

LLM providers are selected through environment configuration. Chart calculation runs as a separate HTTP service, keeping the orchestration backend independent.

NEXT UP

Grounded reasoning

Knowledge retrieval, astrology-source citations, and real Vedic/KP-specific analysis are planned. Today, methodology selection is passed to prompts but does not yet change retrieval or chart logic.

Backend and orchestration

/health and /run are exposed by FastAPI. A run builds immutable request context, invokes the compiled orchestrator graph, and returns the answer, state, and execution trace. Failures from chart or provider calls are surfaced as a gateway error instead of a raw server error.

The orchestrator runs manager, planner, dispatcher, collector, evaluator, and synthesizer stages. Planning chooses specialists and a methodology; evaluation completes once results are available or after a bounded second iteration.

Specialists and state

The shared specialist graph runs planner, executor, collector, evaluator, and synthesizer stages for each requested domain. The executor sends the query, methodology, and chart data to the configured LLM and records structured analysis, conclusion, and confidence results.

The current registry includes career, finance, love, and sports. Shared state carries specialist selection, methodology, chart data, results, errors, and execution progress.

Frontend and accounts

The Streamlit application provides registration, sign-in, a question form, and methodology selection. Birth details are collected at registration, geocoded for India, stored with the account, then submitted with each request.

Accounts use a local SQLite store with scrypt password hashing. This is a development authentication flow, not a production identity system. Date-of-birth uncertainty is captured in the UI, but backend chart handling for an unknown date is not implemented yet.

LLM and context controls

Provider selection supports OpenAI-compatible providers, OpenAI, and Anthropic through environment variables. Provider and model values can be overridden globally, by role, or by specialist. API keys are intentionally kept outside the repository.

Optional context-size protection is available through ASTROWEAVE_CONTEXT_CHAR_LIMIT. When enabled, over-limit hand-offs degrade gracefully instead of allowing a request to fail without a clear state error.

Chart calculation service

Birth-chart calculation is isolated behind a separate FastAPI service. It provides planet positions, ascendant, divisional charts, dasha-bhukti, bhava charts, and ashtakavarga over HTTP; the main backend configures its URL with ASTROWEAVE_CHART_SERVICE_URL.

The service uses PyJHora, an AGPL-3.0 dependency. It remains a standalone service with its own environment and no shared application code, so the orchestration backend stays independently deployable.

Tests and observability

Unit tests cover authentication, routing, specialist execution, dispatcher fan-out, specialist error propagation, and state reduction. Integration tests cover /health and /run with graph calls mocked, so the suite runs without provider keys or chart-service access.

Application logging records request activity and LLM reasoning fields. The Streamlit final-state debug panel is temporary development tooling and is planned for removal when retrieval grounding is in place.

Under active development; not production-ready

07 / the loop

Reasoning can return to the planner.

Results are not treated as finished merely because a tool ran. AstroWeave evaluates whether it has enough information, whether another specialist is needed, or whether another methodology should be considered.

“The synthesizer should not concatenate outputs. It should make the result coherent while preserving meaningful methodological differences.”
