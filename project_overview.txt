ASTROWEAVE - PROJECT OVERVIEW
==============================
Last updated: 2026-09-10

Purpose of this file
---------------------
A plain-language snapshot of what AstroWeave is and what currently exists in
the repo. This is NOT a commit log or changelog - it is a high-level summary
meant to be skimmed by anyone (including future us) who wants to get back up
to speed quickly. Update this file occasionally (e.g. after finishing a
phase of work), not after every small change.

What is AstroWeave
-------------------
AstroWeave is a hierarchical multi-agent astrology system built on LangGraph.
A central "Astrologer Manager" takes a user's question, plans how to answer
it, dispatches work to domain specialist agents (career, finance, love,
sports, ...), applies astrology methodologies (Vedic, KP), collects and
evaluates the results, and synthesizes one final answer.

High-level flow:
  User -> Manager -> Planner -> Dispatcher -> Specialist subgraph(s)
       -> Collector -> Evaluator -> (re-plan if insufficient) -> Synthesizer
       -> Final answer

There are two apps in this repo:
  1. A FastAPI backend (src/astroweave) that will eventually run the
     LangGraph orchestration and expose it over HTTP.
  2. A Streamlit frontend (app/) that provides a simple sign-in/sign-up UI
     and a form to submit a question to the backend.

Current state (skeleton / early phase)
----------------------------------------
The project is intentionally still in a "structure first" phase. Most nodes
are pass-through placeholders; the real astrology reasoning is not wired up
yet. Concretely, as of this writing:

- src/astroweave/api/main.py
    FastAPI app with a /health endpoint and a /run endpoint. /run validates
    the request shape (query, conversation_id, session_id, username,
    methodology) but always returns HTTP 501, since actual execution isn't
    implemented yet.

- src/astroweave/graphs/orchestrator/orchestrator_graph.py
    Builds the top-level LangGraph workflow: manager -> planner ->
    dispatcher -> collector -> evaluator -> synthesizer. Every node is a
    logging pass-through for now; the evaluator conditionally routes back
    to planner or forward to synthesizer based on state["is_sufficient"].

- src/astroweave/graphs/specialist/specialist_graph.py
    Same idea, but for the subgraph shared by every specialist agent:
    planner -> executor -> collector -> evaluator -> synthesizer.

- src/astroweave/common/state/state.py
    Shared LangGraph State TypedDict: messages, plan, tool results, stage
    results (capped at the latest 5), evaluation flags, iteration count,
    errors, final answer, etc.

- src/astroweave/common/context/context.py
    Shared Context TypedDict: conversation_id, session_id, username.

- src/astroweave/common/config/
    Logging configuration lives here (logging.py). configure_logging() /
    get_logger() set up a process-wide logging.basicConfig() the first time
    they're called, controlled by the ASTROWEAVE_LOG_LEVEL env var
    (defaults to INFO).

- Not yet implemented (empty placeholder packages):
    agents/specialists/{career,finance,love,sports}
    methodologies/{kp,vedic}
    orchestration/{dispatcher,manager}
    common/tools
    common/knowledge/retrieval
    common/communication

- app/streamlit_app.py
    Sign in / create account UI (backed by app/auth.py), a query form with
    a methodology selector, and a call to POST /run on the backend. Still
    shows a raw "Final state" / "Execution trace" debug panel for
    development - this is expected to be removed once the app is opened up
    to a general audience, now that backend logging covers that need.

- app/auth.py
    Local JSON-file user store (app/data/users.json) with scrypt password
    hashing and constant-time comparison. Fine for local/dev use, not
    intended as a production auth system.

Logging
-------
Backend and frontend now use Python's standard `logging` module instead of
print statements or debug UI panels:
  - Backend modules get a logger via
    `astroweave.common.config.get_logger(__name__)`, which configures the
    root logger on first use (format: timestamp, level, logger name,
    message). Level is controlled by the ASTROWEAVE_LOG_LEVEL env var.
  - The Streamlit app configures logging.basicConfig() directly at import
    time and logs request submissions, API responses, and connection
    errors.
  - Graph nodes log at DEBUG when they execute (useful once real logic
    replaces the pass-throughs); the API logs at INFO/WARNING for request
    handling.

Tests
-----
tests/unit - auth logic, orchestrator graph routing, specialist graph
routing and the "keep latest five stage results" reducer.
tests/integration - /health and /run behavior against the FastAPI app.
Run with: PYTHONPATH=src pytest tests/

How to run locally
-------------------
Backend:  PYTHONPATH=src uvicorn astroweave.api.main:app --reload
Frontend: streamlit run app/streamlit_app.py

Chart calculation service (chart_service/)
--------------------------------------------
Birth chart math (planet positions, ascendant, etc.) is powered by PyJHora, a
mature Vedic/KP astrology library. PyJHora is licensed AGPL-3.0 (the PyPI page
mislabels it as MIT - the actual bundled license text is AGPL-3.0). AGPL's
network clause means a program that imports it in-process and is offered as a
network service must release its combined source under AGPL too.

To avoid pulling that obligation onto the whole AstroWeave backend, PyJHora is
isolated in its own standalone service, chart_service/ (own requirements.txt,
own FastAPI app, no shared code with src/astroweave). It only communicates
with the rest of the system over plain HTTP:

  POST /chart  { date, time, latitude, longitude, utc_offset_hours, place_name,
                 varga_factors?, include_dasha_bhukti?, include_bhava_chart?,
                 include_ashtakavarga? }
  -> {
       d1: { ascendant, planets } (sign/degree per planet, each with KP sub-lord chain),
       divisional_charts: { D9, D10, D7, D12, D3, D24 by default, or whichever
                             varga factors were requested } (sign/degree per planet),
       dasha_bhukti: [ { maha_lord, bhukti_lord, start_date, start_hour, duration_years }, ... ],
       bhava_chart: [ { sign, house_start/cusp/end_longitude, planets }, ... one per house ],
       ashtakavarga: { binna: { <planet>: [12 points per sign] }, samudhaya: [12 totals] },
     }

Run it with:  uvicorn chart_service.main:app --port 8100
The main backend calls it via astroweave.common.tools.chart_client.get_birth_chart(),
configurable through the ASTROWEAVE_CHART_SERVICE_URL env var (defaults to
http://127.0.0.1:8100). PyJHora's core chart/panchanga modules work headlessly
(no PyQt6 needed) - only its desktop UI widgets require Qt, and those are not
used here.

What's next (not a commitment, just current direction)
